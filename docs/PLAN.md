# Hearthlog implementation plan

## Low-volume MVP rationale and evolution
SQLite is deliberately the initial store for a low-volume, single-node MVP: one deployable Go service with local durable storage is simpler to operate than a separate database server. Go and htmx remain the interface stack. PostgreSQL is a future option if observed needs justify a separate service, not a second MVP implementation or an automatic migration.

Separate storage functions into a small SQLite-focused package from domain validation, ingest/query contracts and HTTP/template handlers. Pass typed inputs/results and context; keep SQL/FTS/PRAGMAs/checkpoint/backup details out of handlers. Do not build a generic multi-backend framework, plugin registry, dual-write path or speculative PostgreSQL schema. Preserve immutable event IDs, workspace/source identity, native batch IDs/hashes, timestamp/type semantics, versioned envelopes and cursor invalidation epochs. Document a future export/reimport validation recipe for counts, IDs, ordering and receipts, without implementing migration now. Cursors are opaque and store-specific; changing store must explicitly invalidate them.

## Scope and initial architecture
Go + SQLite + htmx. One Go process, one local persistent SQLite database, server-rendered HTML via Go html/template, embedded CSS and pinned self-hosted htmx 2.x assets. No frontend build pipeline or separate database service. This is a logs-only single-node system, not a metrics/tracing platform, SaaS, distributed log warehouse or compliance archive. Trace/span IDs are optional log correlation fields only. Infrastructure purchase, real-app adoption and production rollout are outside implementation acceptance.

Use net/http and database/sql with a pinned SQLite driver exposing online backup, cancellation/interrupt and FTS5. Recommend mattn/go-sqlite3 with bundled SQLite and CGO/fts5 build support; prove actual linked SQLite version and compile options rather than trusting driver version. Require SQLite >=3.51.3 (or an independently documented patched release) because official WAL docs describe a WAL-reset corruption fix. Runtime probes must exercise FTS5 and JSON functions and verify PRAGMAs on new connections. CGO packaging and target support are a Slice 00 decision, not permission to change the fixed stack. Do not dynamically load arbitrary extensions.

## Investigation workflow
Better Stack Telemetry's documented source selector, time picker, query/filter flow and expandable attributes are interaction references only. Build original layouts/colors/copy without copied assets. Source sidebar; time/severity/message-token search; dense timestamp/level/source/message list; typed nested detail panel with filter-on-value and copy-redacted-JSON. Search and Live are visibly separate. Saved views retain sources/filters, not a frozen relative-time evaluation. Default 15m range, explicit absolute window on results; event and receipt timestamps distinguished.

Keyboard navigation and labels work; severity uses text, focus returns from details, narrow screens preserve controls. Historical query submission/detail/pagination works as ordinary HTML forms/links without JavaScript; Live requires htmx and has manual refresh fallback.

## SQLite concurrency, durability and transaction design
One application instance holds the database ownership lock; a second service process refuses startup. Database is on local durable storage, never a network filesystem. Normal writes, source/session/view changes and retention run through one bounded scheduler and one dedicated writer connection. Admission queue max 64 jobs AND 16MiB payload bytes; request admission wait <=100ms, full returns 503/Retry-After. Scheduler gives every pending maintenance class a turn after at most 10 ingest jobs; quotas stop one source starving others. No request handler directly opens a second writer. Reader pool max 4 query-only connections, no shared cache; bounded connection caches and response buffers. An online-backup source connection is separately capped at one.

Set and verify journal_mode=WAL, synchronous=FULL on writer/maintenance-capable connections, foreign_keys=ON on every connection, busy_timeout=250ms per connection, locking_mode=NORMAL. Set auto_vacuum=INCREMENTAL before schema creation. Keep wal_autocheckpoint=1000 pages initially and observe commit tails; also schedule PASSIVE checkpoints after write bursts and at least every 5s while active, never concurrently with another checkpoint. Record busy flag/frame counts, WAL bytes and oldest reader age. journal_size_limit is NOT an active WAL hard cap. Reads end after bounded materialization, before HTML rendering or network response; no DB snapshot spans pagination, polling, user think time or slow sockets.

At 64MiB WAL or 30s checkpoint lag, stop admitting new searches briefly (<=1s) to create reader gaps, cancel over-deadline readers, and attempt a scheduler-controlled bounded checkpoint. Above 256MiB WAL or disk reserve threshold stop ingest with explicit 503 until recovery; these provisional limits cannot prevent one in-progress transaction growing the file. Never delete WAL or shared-memory sidecars. RESTART/TRUNCATE checkpoint only in a coordinated reader gap with bounded busy handling, not on every request. Failed checkpoint is observable, not success. SQL_BUSY/LOCKED is retried only within the request budget with jitter and whole-transaction restart where needed; no infinite retry or retrying a half-applied operation. Uncertain commit is resolved by native receipt lookup/replay, not a fresh batch ID. Read cancellation must demonstrably interrupt SQLite and close rows, not merely abandon an HTTP goroutine.

Native ingest validates before admission. BEGIN IMMEDIATE on writer; atomically insert immutable log rows, FTS entries, batch receipt and persisted commit watermark, then COMMIT. HTTP 200 only after successful FULL-synchronous commit. Durability assumes honest filesystem/device sync semantics and surviving storage; host/disk loss requires backup recovery. Client queues and unacknowledged batches may be lost on crash; no durable client spool in v1.

## Data, receipt and isolation model
One workspace initially; second workspace exists in isolation fixtures. Source is registered application+environment; instance ID is metadata. Native schema: version, event_id, event_time, severity number/text, message, typed JSON attributes, optional trace/span IDs. Server supplies workspace/source from credential, received_at, ingest_id and service/environment from registration. Reject reserved-key override, duplicate JSON keys, invalid UTF-8/nonfinite numbers, bad IDs, excessive nesting, timestamps >5m future or older than configured horizon. Store timestamp integers in UTC; present an explicit UI zone. Retention uses receipt time, independent of event clock.

Store RFC-8259 attributes as validated TEXT with json_valid check, not opaque binary format. Require json_type as well as json_extract for equality: missing differs from null, bool differs from number, string differs from integer. Restrict v1 numeric contract to signed 64-bit integers and finite float64, reject out-of-range values rather than rounding silently. Nested paths are parsed segments with length/depth bounds and bound as values, not SQL fragments. Exotic-key support must have roundtrip fixtures or return an explicit unsupported-path error.

Use INTEGER PRIMARY KEY AUTOINCREMENT ingest_id for immutable rows. The single writer allocates IDs inside its transaction: no later transaction can commit a higher ID first. Persist a highest-committed-ID watermark in that same database/transaction, retain it despite retention deleting every log; no cursor reset/reuse. Rollback holes are harmless, acknowledgments wait for commit. Recovery loads committed watermark. No separate in-memory counter is authoritative.

Receipt UNIQUE(workspace_id,source_id,batch_id) + canonical payload hash; same key/same content returns original result, changed content returns 409. Receipts and events/FTS commit together. Receipts retained >=48h, native retry horizon 60s. Midnight does not change receipt identity. Receipt expiry/new batch IDs/manual rebatching may duplicate events: promise only batch retry idempotency within 48h, not global event exactly-once. Whole-batch reject malformed content; no partial silent acceptance. OTLP has a separate weaker guarantee below.

SQLite has no database-enforced tenant row policies: application repository methods require authenticated workspace scope and every SELECT/JOIN/UPDATE/DELETE includes it, including FTS joins, detail, views, source admin and live cursors. Never expose raw SQL or file download endpoints. Filesystem permissions on DB/sidecars/backups limit access to service/operator; SQLite files are not encrypted by default, require encrypted host volume and encrypted backups for sensitive deployments. This is single-operator deployment isolation, not a hardened shared-host database service.

## SDK reliability and pre-transmission privacy

Use normal slog API; handler implements Enabled, Handle, WithAttrs, WithGroup correctly under concurrency. Snapshot/resolve/redact data synchronously into owned bounded representation; do not retain mutable application values for later evaluation. Cancellation of request context must not drop a diagnostic event; sender has its own lifecycle context. Logging never waits for network. Errors returned from Handle are generally ignored by slog, so expose counters and a non-recursive diagnostic hook.
Provisional defaults: queue max 2,048 events AND 8 MiB serialized bytes; max event 32 KiB, nesting 8, 128 attributes; drop newest on overflow, count by reason/severity; no priority queue guarantee. Sender batches max 200 events or 256 KiB uncompressed, whichever first, every 250ms; two requests in flight maximum; request deadline 5s. Retry 429/5xx/network ambiguity with exponential jitter 250ms–5s and Retry-After bounded by remaining 60s retry budget. Do not retry 400/401/403/413 indefinitely. No automatic splitting that changes a batch identity after ambiguity. Compression bounded on compressed AND decompressed bytes at server. Flush(ctx) waits for events accepted before the call; Close(ctx) stops acceptance and drains with deadline, returns unsent count/error; idempotent and race-tested. SIGKILL may lose queued/in-flight unacknowledged events. Local fallback, if enabled, contains only already-redacted events, is rate-limited and explicitly does not provide replay.
Counters/hooks: queued bytes/events, sent/acked, retries, dropped(reason), redaction failures, shutdown unsent; server accepted/rejected/deduped, ingest latency, query latency/timeouts, live gaps, disk headroom/retention lag/checkpoint backlog/backup age. Bounded labels only; never label by event ID, raw query, token or message. This operational instrumentation is not a metrics product.


Token scopes are server-authoritative. Redaction defaults strip authorization/cookie/password/token keys recursively; default-drop bodies/headers and require allowlisted arbitrary objects. Message pattern scrubbing and app-specific hooks supplement “do not log secrets”; generic free text cannot be guaranteed PII-free. Canary tests cover messages, groups, WithAttrs and custom LogValuer; prove no secret on wire, local fallback, DB, rendered HTML, FTS or diagnostics. Server redaction is defense in depth, never a substitute for redaction before transmission. Fail closed on redaction/conversion failure and count reason, never raw-payload stderr dumps.

## Search, indexes and bounded scans
Core indexes: (workspace,source,event_time,ingest_id), (workspace,event_time,ingest_id), (workspace,ingest_id) and (received_at,ingest_id) retention index. FTS5 external-content index covers redacted message only; transactional insert/delete triggers maintain it from immutable logs. Verify FTS integrity including external content; rebuild only in planned maintenance. Match joins always reapply authorized workspace/source. Do not mark raw FTS highlight output trusted HTML.

Token search uses unicode61 with documented case/diacritic behavior and <=8 literal terms, escaping embedded quotes and constructing a bound AND-of-quoted-terms MATCH expression. No raw FTS operators, regex, substring LIKE fallback or relevance sort in v1. Historical order is (event_time DESC, ingest_id DESC) with keyset predicates, never OFFSET. First response freezes highest committed ingest_id and receipt cutoff in signed cursor; subsequent pages use that horizon without keeping a read transaction open. Expiry 15m. Cursor binds workspace, sources, filters, last tuple, horizon and retention cutoff. Retention crossing frozen cutoff invalidates cursor and requests rerun rather than silently incomplete “snapshot.” Authorization rechecked every page.

Up to 8 typed attribute predicates; arbitrary JSON predicates run only inside indexed workspace/source/time candidate scans with explicit progress/VM-step and time budget. Start at 100,000 VM steps per statement (provisional; calibrate without silently raising), 3s DB/5s HTTP and <=4 searches/workspace globally limited by four readers. Exceeding budget returns query-too-broad with narrow-window guidance, not “zero matches.” Common vetted attribute paths may receive a small fixed set of expression/generated-column indexes after EXPLAIN evidence; no per-user dynamic index creation. FTS common-token intersections may also exceed budget: reject honestly, do not assume FTS guarantees bounded work. 4KiB input, 200 rows/2MiB serialized response; no count-all scan. EXPLAIN QUERY PLAN + progress-budget tests prove index use and predictable rejection. Writer admission, read concurrency and maintenance remain separately bounded.

## Server-rendered htmx interface and Live
All full pages/partials use trusted static html/template templates; untrusted messages/keys/values only data, never template.HTML/JS/URL. htmx targets and request URLs are fixed routes, not log attributes. Normal requests return complete pages; HX-Request can select partials but is never authorization. Use Vary: HX-Request and Cache-Control: no-store on authenticated pages/fragments. Disable history snapshots (hx-history=false and historyCacheSize=0), historyRestoreAsHxRequest=false; full URL navigation returns full authenticated page. Raw query strings are omitted from logs; Referrer-Policy:no-referrer. Warn that copied filter URLs may contain sensitive terms; no telemetry or persistent browser log cache.

Self-host pinned htmx asset; selfRequestsOnly=true, allowEval=false, allowScriptTags=false, reportValidityOfForms=true, finite request timeout. Strict same-origin CSP with external static event listeners (no inline handlers/eval); escaping prevents hx-/data-hx-attribute injection. CSRF validation for all state-changing requests including htmx, rotate/session-bound hidden token forms; POST never changes state without token/origin checks. Minimal unbundled JS only for focus/clipboard, error display and bounded Live bookkeeping; no client application state framework. Use request synchronization/cancellation and query-generation IDs to discard stale partials. Handle send/response errors explicitly since htmx does not swap 4xx/5xx by default. aria-live announces status, not every log line.

Live uses hx-trigger every 1s, at most one outstanding poll/tab, max two active live clients/workspace. Fetch <=200 committed rows by ingest_id > cursor and <= captured committed watermark. Cursor advances to highest examined authorized scan position (not just last matching row) so sparse filters progress; cap scan work and emit explicit gap if budget exhausted. Keep filters stable per live generation, dedup by ingest_id. Server renders escaped row partials; small external after-swap handler appends/prunes to 1,000 rows and updates cursor/count/status, verified before next poll. Pause cancels polling and freezes rows without building a backlog; resume within <=5,000 events/30s supported catchup, otherwise gap + historical-search action. Closed/hidden tabs stop polling; revocation/timeout/disconnect visibly stop or back off, never spin. DB connection closes before waiting for network. Live is not an export guarantee.

## Authentication and source lifecycle
Synthetic loopback slice uses separate read/write credentials. Before remote or real logs require TLS plus operator-chosen OIDC code+PKCE, issuer/audience/redirect validation, secure HttpOnly SameSite server sessions, CSRF and explicit membership allowlist. Workspace operator/reader roles; readers see all workspace sources, no per-source ACLs in v1. Source tokens random, write-only, hashed, scope-bound, displayed once, overlap rotation/immediate revoke supported. No token in URL, UI asset, logs, issue or source. Auth/session DB writes use writer scheduler and fail closed on overload; revocation checked each query/poll. Source requests rate-limited by bounded token buckets; limits and denied reads observable without recording payloads. Two-workspace negative tests are mandatory.

## Retention, disk reclaim and recovery
Provisional seven-day receipt-age retention: search/live exclude expired logs immediately even if cleanup lags. Once/minute select <=1,000 expired IDs by received_at index and delete in <=100ms-target writer transactions, yielding between chunks. FTS deletion and log deletion remain transactional; receipt cleanup separately keeps >=48h. Target cleanup lag <=10min under baseline; if lag grows, alarm and throttle ingest instead of unbounded DELETE. Index/service work remains bounded; large FTS merges/optimize are maintenance tasks with explicit budgets, not interactive-request surprises.

Deleted pages normally become reusable, not automatically a smaller file. Set INCREMENTAL auto-vacuum at initialization; schedule <=256-page incremental_vacuum steps in writer gaps with deadline and observe freelist/file/WAL size. Shrink is not secure erasure. TRUNCATE checkpoint in reader gaps reclaims WAL separately. Do not run whole-db VACUUM on live request path; an explicit maintenance window, free-space preflight, backup and stop-ingest procedure is required for major rebuild. No manual sidecar deletion. Retention does not promise forensic erasure from freed pages, FTS remnants, WAL, snapshots or backups; privacy policy requires pre-transmission redaction and documented backup expiry.

Disk guard at 20% free or configured byte reserve, whichever more protective; account for database + FTS + WAL + temp + backup destination. Reject ingest with 503 before exhaustion, no silent early retention deletion. Queries remain available if safe. Run disk-full/busy/checkpoint-starvation drills on disposable fixtures, never production.

Use SQLite Online Backup API in incremental steps to unique temporary destination through selected driver; source is a dedicated connection, one backup max, bounded busy retries/overall timeout, progress and restart monitoring. Writes may restart backup: timeout reports failure and backup-age alarm, not completed snapshot. After sqlite backup finishes successfully, close destination, sync completed snapshot and parent directory as applicable, validate integrity_check/foreign_key_check + FTS external-content consistency and sentinel counts, compute checksum, encrypt and atomically publish snapshot + capture interval/schema metadata. No cp of open main database, no separately racing copies of db/wal/shm. Keep last verified snapshot on failed backup. Backup destination credentials/keys never in repository.

Provisional hourly backup, completion <=5min; maximum tolerated age of verified off-host snapshot's conservative capture start <=2h, intended RPO <=2h and RTO <=60min, measured not guaranteed. No point-in-time recovery or continuous archive in v1. If snapshot cost fails single-node gates, reduce supported workload or revisit recovery requirements explicitly, not silently weaken durability. Encrypt off-host snapshots and expire after seven days; expired logs may remain until backup expiry. No object-store account or paid destination created by these slices.

Restore into a new isolated directory/database while service stopped: verify checksum/decrypt offline, validate integrity/FTS/receipts/watermark/memberships, initialize expected settings, reconcile monotonic cursor epoch (invalidate all pre-restore cursors), compare sentinels, then deliberate promotion. Never overlay live main DB with stale sidecars. Preserve old directory for rollback; do not automatically reuse sessions/credentials if recovery policy requires rotation. Schema migration preflight backup, compatibility test and rollback via stopped-service verified snapshot; no destructive downgrade.

## Proportionate MVP validation and optional stress envelope
These are synthetic validation profiles, not facts about an existing application's volume. Low-volume baseline is a provisional test profile of 50,000 events across three generic sources (~1KiB/event average), 5 events/s for 30min and a brief 50/s burst for 10s, one historical reader and one Live reader on a declared modest local test environment. Record actual test resource limits, but do not require a purchased host or a fixed CPU/RAM class. Before real adoption validate expected volume/size and adjust the baseline through an explicit documented decision if needed.

Required MVP acceptance:
- Baseline native batches have no unexplained acknowledged loss or duplicates within receipt window; any overflow/rejection/drop is visible and counted. Handler p95 <1ms for bounded values, endpoint outage 5min RSS delta <64MiB, flush/close bounded. Test five deterministic kill/restart/replay cycles covering before commit, post-commit/pre-response and replay, including rollback/midnight/expiry fixtures. FULL-sync/driver settings and honest storage assumptions documented; process kills alone do not prove power-loss immunity.
- Representative source/time/literal-token/typed-attribute first pages p95 <1s, every query finishes/aborts <=5s; Live p95 visibility <2s, 1,000-row DOM bound and explicit gaps. Broad queries are resource-budget rejected honestly, not “zero matches”; representative baseline queries must actually succeed.
- Retention, checkpoint, backup and baseline reads coexist without indefinite writer/read queues. Idle checkpoint backlog clears <=10s, cleanup lag <=10min; pressure/busy/disk guards use a smaller disposable fixture when sufficient to exercise the failure path. Verify FTS/SQLite consistency after deletes/restarts. No 1M-row dataset or sustained high throughput is prerequisite to low-volume MVP readiness.
- Complete one online backup under baseline writes and one isolated restore; verify counts/IDs/receipts/watermark/identity state and explicit cursor invalidation. Provisional snapshot schedule is hourly, target completion <=5min, maximum allowed verified off-host snapshot capture-start age <=2h and intended RPO <=2h/RTO <=60min. Report observed times and mark recovery unready if no verified destination exists. A stricter operator requirement needs an explicit plan adjustment, not a pretend guarantee.
- Security/privacy do not relax with volume: cross-workspace/full-page/partial/FTS/cursor/live/source tests, CSRF/auth/template tests, secret scanning and canary absence on wire/store/FTS/rendering/snapshot/evidence all required. Local synthetic development remains distinct from approval for remote or real logs.

Optional diagnostic stress envelope, not an MVP release gate: 1M events/10 synthetic sources, 100/s 30min and 1,000/s 60s burst, two readers plus backup/retention/checkpoint, 20 crash/replay cycles and larger backup/reclaim tests. Run only when useful to capacity planning; publish raw accepted/retried/rejected/dropped counts, CPU/RSS/disk/WAL/VM steps and p95/p99. Reaching this envelope or passing it is not claimed. Optional failures cannot silently waive baseline safety or accepted-data durability.

Reconsider PostgreSQL in a documented architecture review when any measured condition occurs:
- Requirement for a second active service node, shared remote database access or HA appears; SQLite WAL is same-host/single-writer and not a network filesystem service.
- For three representative 15min observation windows, normal expected load yields >1% ingest busy/admission rejections or writer queue wait p95 >100ms despite bounded batch/checkpoint/index tuning; intentional outage/stress drills excluded.
- Representative bounded queries p95 >1s or >1% budget rejections in three windows, despite evidence-backed index/time-window tuning, or read pauses needed for checkpoint progress become recurrent (>1/min for 15min).
- Retention cleanup lag >10min, checkpoint lag >30s recurs, projected seven-day footprint + indexes/WAL/backup working space exceeds 70% of provisioned storage, or verified backup capture age/RPO fails twice consecutively at normal load after bounded remediation.
- Measured operational/recovery needs require capabilities outside this single-node snapshot model.
These are investigation triggers, not automatic migration, not claims PostgreSQL will solve every issue and not reasons to reject a small healthy MVP. Collect plans/latencies/volume/resource evidence, compare tuning or capacity changes against a small PostgreSQL benchmark proposal, and get a deliberate decision before new backend, export or migration work. Never implement a second backend merely to anticipate growth.

Actual workload/runtime, hosting/budget, identity/access, redaction/retention/recovery and pre-ack loss decisions remain operator prerequisites. After separate rollout approval: one staging app observation 24h retaining prior safe logging, then a low-risk app 48h; compare known generated counts/overhead/loss and expand only with evidence. Feature-disable and token revoke are rollback paths. No deployment, paid resource or real app changes in planning work.

## Final deliverable: deployable MVP and service integration
By completion of the twelve slices, deliver a versioned, buildable deployable binary for each explicitly declared and tested target—not a universally static executable. Slice 00 declares initial GOOS/GOARCH, Go toolchain, CGO compiler/libc/runtime requirements and bundled SQLite version/FTS5/JSON support; an initially narrow tested target is sufficient. Reproducible build commands must describe toolchain inputs, dependency lock/pins and asset embedding, produce version metadata and SHA-256 checksums, and verify SQLite runtime version/features plus startup health. Do not invent build commands or platform support before implemented and tested. A supported target is selected through a documented technical decision; additional platforms are out of scope until verified.

Provide generic Markdown deployment instructions covering binary verification/install, nonprivileged service identity and filesystem permissions, persistent local SQLite directory and WAL/SHM ownership, disk headroom, runtime/CGO prerequisites, listener/TLS/reverse-proxy and OIDC/source-token settings as placeholders only, secure initial provisioning, startup/readiness checks, service supervision/restart and safe stop. Include verified backup/isolated restore, versioned schema migrations, pre-upgrade snapshot, upgrade health validation and stopped-service rollback/compatibility boundaries. No live environments, environment files, actual secrets or app-specific configurations.

Provide a service-integration guide with a compilable synthetic Go slog example and reproducible commands using the published SDK version. It must show generic endpoint placeholder, source provisioning/write-token rotation/revocation, redaction before enqueue, grouping/attributes/context correlation, bounded batching/retry/drop behavior, Flush/Close with shutdown deadlines and unsent/error counters, safe staged rollout and immediate remote-logging disable while preserving prior safe logs. Logs-only OTLP guidance must cover only the implemented pinned and verified protocol subset, explicit supported encoding/exporter/resource mapping and weaker duplicate guarantee; no metrics/traces or blanket compatibility promise.

Final fresh-install acceptance uses the produced versioned binary in a clean isolated local test directory with no implementation shortcuts: an independent tester follows only written docs to verify checksum/runtime, provision synthetic credentials locally (never publish values), start service, integrate/build the synthetic demo service, emit a marked redacted event, find it through search/detail and Live, restart the service and prove the event persists, then run backup/restore and documented safe disable. Record exact documented commands, target/toolchain/SQLite features, binary version/checksum, sentinel IDs/counts, UI evidence and sanitized results; missing instructions or hidden manual steps fail acceptance. This is a requirement, not a claim a binary or those tests exist today. No actual production deployment is authorized.

## Official source evidence
Public docs read November 7, 2026 (MST):
- https://sqlite.org/wal.html — one writer, same-host WAL, long readers prevent checkpoint completion, WAL is persistent state; FULL syncs each commit; WAL-reset fix in 3.51.3 and documented backports.
- https://sqlite.org/pragma.html — busy_timeout, synchronous, query_only, auto_vacuum/incremental_vacuum, checkpoint modes and journal_size_limit semantics. These settings must be read back; unknown PRAGMAs can be silently ignored.
- https://sqlite.org/fts5.html — FTS5 build support, MATCH syntax/literal quoting, unicode61, external-content consistency/triggers, integrity checks and merge overhead. We deliberately do not expose its full grammar.
- https://sqlite.org/json1.html — TEXT JSON, json_valid/json_extract/json_type and type distinctions support portable attributes and explicit equality semantics.
- https://sqlite.org/backup.html — incremental online backup API supports live use but writes can restart it indefinitely; bounded backup and verified completion required. VACUUM INTO is an alternative, not the default online job.
- https://htmx.org/docs/ — HTML partial responses, polling, swapping, synchronization, full-page history restoration, non-swapped error defaults, escaping/CSRF and history-cache security settings; no build system needed.
- https://pkg.go.dev/html/template — contextual escaping, trusted templates/untrusted data; bypass string types introduce security risks.
- https://pkg.go.dev/log/slog — concurrent handler methods, ignored Handle errors, group/value/context rules and pre-log modification hooks.
- https://opentelemetry.io/docs/languages/go/instrumentation/ — existing-library bridges, batching/export/shutdown and stdout forwarding workflow. Direct-to-Collector docs label workflow Experimental; compatibility must be pinned/tested, not assumed.
- https://betterstack.com/docs/logs/using-logtail/querying-data-in-logtail.md — public illustrated source/query/time controls, saved views and attribute explorer; inspiration only, no authenticated UI access or copied assets.
